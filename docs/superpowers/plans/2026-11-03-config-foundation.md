# Config Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Split configuration into three portable domains (App, Planner, Calendars), edited through one `GET`/`PATCH` pair per domain over a safe write path, with no configuration or credentials stored in the database.

**Architecture:** A config directory holds one YAML file per domain plus a local-only login file. A `config.Service` reads and patches those files (merge-patch, validated per domain, written atomically under a mutex, comments preserved). Changes take effect on restart. The SQLite DB holds only rebuildable state.

**Tech Stack:** Go (module `github.com/Kenttleton/focacal`, go 1.26.0), chi, viper (read at startup), `gopkg.in/yaml.v3` (`yaml.Node` for comment-preserving writes), modernc/SQLite store (unchanged by this plan).

**Spec:** `docs/superpowers/specs/2026-10-30-calendar-foundation-and-planner-design.md` (sections 4.4, 5.1, 9.5). The decisions below were made with the owner on 2026-11-03 and extend it.

## Decisions (owner, 2026-11-03)

- **Portability comes first.** The config directory alone must be enough to stand up a new instance: copy it, re-authorize the calendars (`focacal auth`), and Focacal regenerates its events into an empty DB. So the DB holds only rebuildable state (event cache, generated blocks, sync tokens, OAuth tokens, dismissals) and never config.
- **Three domains**, each its own file: **App** (`config.yaml`: server, agent, oauth, `auth.enabled`), **Planner** (`planner.yaml`: working hours and zone, lunch, focus, generated-event colors), **Calendars** (`calendars.yaml`: sources, destinations, per-calendar colors).
- **One `PATCH` per domain**, piece at a time. Collections (`sources`, `destinations`) are id-keyed objects in the API (`null` deletes) and stay YAML lists on disk.
- **No secrets through the API.** Credentials stay in `.env` or referenced files (spec 9.5). `PATCH` rejects inline `password` and `ics_url`.
- **Changes apply on restart** (spec 9.5). `GET` returns the saved values plus `pending_restart`. No live in-memory mutation.
- **Login credentials** (`username`, `password_hash`) move to `credentials.yaml` in the config directory: portable by copying, git-ignored, mode 0600. `session_token` is deleted (written today, never read). The file doubles as the **recovery mechanism** for a single-user, file-access deployment: copying it ports the login to a new instance; deleting it reopens first-run `/auth/setup` so new credentials can be created, after which the DB can be wiped and rebuilt.
- **The directory mount is mandatory** (project is in development; the owner is the only user), so there is no compatibility path for the old single-file mount beyond the in-place write fallback in Task 2.
- **Time zone:** `working_hours.timezone` stays in Planner. The client's display zone is client-only; `display_timezone` is removed.
- The planner rules reshape (Routine/Focus/Transition) is **not** in this plan. `lunch` and `focus` move as-is into `planner.yaml`, marked legacy.

## Global Constraints

- Config edits stay behind the existing auth middleware (spec 9.5).
- Credentials stay in `.env` or credential files referenced by path or env var, including secret ICS feed URLs (spec 9.5).
- Ids for sources and destinations may be generated by the UI or hand-written, and must be unique (spec 4.4, 8).
- Comment preservation is best effort (spec 9.5).
- The `Store` interface takes no user id (see `internal/store/store.go`).
- Focacal never writes to external calendars in this phase (spec 6).

## Review Focus

- **Single-file Docker bind mount:** `./config.yaml:/data/config.yaml` makes `rename` onto the file fail with `EBUSY`. The writer must fall back to an in-place write (with a `.bak` copy), and the new layout mounts a directory.
- **Deleting a source that a destination references** (`{"sources": {"work-google": null}}`) must be rejected with a validation error and leave files untouched.
- **Hand-edited files:** unknown keys (such as the unread `ollama:` block), comments and key order outside the patched keys must survive a patch unchanged.
- **Bad request bodies:** wrong types, unknown fields, empty body, a body over 1 MiB, and `null` for a required scalar all return an error and never touch the file.
- **Concurrency:** parallel `PATCH` calls plus a login must not lose an update or corrupt a file (run with `-race`); two simultaneous first-run `/auth/setup` calls must not both succeed.

## Out of scope (separate plans)

- **Colors:** per-calendar colors and the by-type palette for generated events (fields live in these config files; the UI and API work is its own plan).
- **Pages:** Planner and Settings page content, and the new sources/destinations page (name still to be chosen).
- **Timezone input** typeahead with abbreviations and long names, and the rounded-triangle now-marker.
- **US holidays** as a built-in ICS source preset (see the research notes in conversation: Google's public feed, with all-day timezone handling as the first test).
- **Planner rules reshape** (Routine/Focus/Transition, priority bands).
- **Multiple concurrent sessions per user** (today a login issues a token and keeps the older ones valid for the process lifetime).
- **Manually created or locked blocks** live in the DB and are not regenerated on a fresh instance; whether they belong in config is a later decision.
