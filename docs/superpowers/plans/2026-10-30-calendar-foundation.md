# Calendar Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish the read-only calendar foundation: accounts and destinations config, a link layer that replaces delete-based dedup, per-source conflict detection, an ICS source, event-type colors, and config editing through the REST API and web UI.

**Architecture:** Connectors write one store row per source, calendar and uid, carrying iCalUID, response status and busy/free. Linking, canonical selection and conflict detection are computed on demand from those rows by two small pure packages (`internal/calendar`, `internal/conflict`), so nothing derived is stored except conflict dismissals. Every consumer (REST, CalDAV emitter, MCP) reads the canonical merged list through one helper. Config is parsed and validated in `internal/config` and written back to `config.yaml` by a YAML-node writer that only touches the sections it owns.

**Tech Stack:** Go 1.23, SQLite (modernc), chi, cobra/viper, `gopkg.in/yaml.v3` (promote from indirect), `github.com/emersion/go-ical` and `github.com/teambition/rrule-go` (already indirect), stdlib `testing` and `net/http/httptest` only (no new test libraries).

**Spec:** `docs/superpowers/specs/2026-10-30-calendar-foundation-and-planner-design.md` (sections 4.1 to 4.5 and 9). Planner and outputs (spec sections 3.2, 3.3 and 5) are out of scope.

## Global Constraints

- Module path is `github.com/Kenttleton/focacal`; Go `1.23`.
- Read-only: no write to any external calendar. `destinations:` is parsed, validated and stored but `event:` visibility rules are applied to nothing. Focacal's own feeds (CalDAV, REST, MCP, UI) show everything unobscured.
- `title` and `body` visibility semantics: `visibility: false` leaves the field empty; `visibility: true` with no `rename` passes the text through; `visibility: true` with `rename` shows the rename text; omitting `event`, `title` or `body` equals `visibility: false`.
- Destination `calendar_id` must be in the account's `calendar_ids`. Ids (source ids, destination `id`+`calendar_id` pairs) are unique; they may be generated by the UI or hand-written.
- Conflict switches are per source config: declined, tentative, free/transparent, all-day. An overlap fires only when both events are positives under their own source's settings. Dismiss means "seen" only. Focacal never resolves or writes to fix a conflict. Generated events yielding to meetings is not a conflict.
- Conflict defaults (spec call): declined no, free/transparent no, tentative yes (marked tentative), all-day no unless marked busy. Rows linked as the same meeting never conflict with each other.
- Event row id is `{source_id}:{calendar_id}:{uid}`. Link key is iCalUID plus instance start. Fuzzy fallback: identical start and end plus normalised title, flagged heuristic.
- Canonical row for linked rows comes from the earliest-declared account in config order.
- Colors follow event kind: meeting, focus, routine, transition, plus a conflict marker. Default palette is 5 colors; custom hex or `rgb(r,g,b)` allowed. ICS `COLOR` (RFC 7986) is a CSS3 color name, so exact colors map to the nearest name; the exact color stays in the UI and REST API.
- Reuse no Reclaim names. User-facing copy says "Routine", "Focus", "Transition", "priority" bands only; do not introduce Habits, Buffers, or four-tier priority.
- Credentials stay in `.env` or credential files. Secret ICS feed URLs and passwords never appear in REST responses or logs.
- Polling stays at 5 minutes. Webhooks are off by default.

## Review Focus

Inputs and conditions the spec implies but no requirement states; each gets a pinning test in the task named.

- Events with an empty iCalUID (CalDAV without UID, Outlook null) must never link to each other: Task 7.
- Back-to-back meetings (end equals next start) and zero-duration events are not conflicts and must not panic: Task 8.
- An ICS URL that returns 200 with an HTML login page, an empty body or a 5xx must fail the sync and leave existing rows untouched, not wipe the calendar: Task 6.
- A secret ICS URL or CalDAV password must not appear in `GET /sources` output: Task 10.
- A read-only `config.yaml` mount, or a config containing comments and unknown keys, must give a clear error or be preserved byte for byte outside the edited section: Task 11.

### Task 8: Conflict detection and dismissals

**Files:**
- Create: `internal/conflict/conflict.go`, `internal/conflict/conflict_test.go`

**Interfaces:**
- Consumes: Task 7 `calendar.Link`; Task 1 `ConflictConfig` accessors; Task 3 `Event.IsTentative`, `ListDismissedConflicts`.
- Produces:
  - `type Conflict struct { Key string; A, B calendar.Link; Tentative bool; Dismissed bool }`.
  - `func Positive(e *store.Event, cfg config.ConflictConfig) bool`: false for declined unless `CountsDeclined()`; false for `ShowAs=="free"` unless `CountsFree()`; false for tentative unless `CountsTentative()`; for all-day events, false unless `CountsAllDay()` or `ShowAs` is `busy`/`oof`... (spec call: with the all-day switch off an all-day event counts only when marked busy; with it on, normal rules apply.)
  - `func LinkPositive(l calendar.Link, bySource map[string]config.ConflictConfig) bool`: true if any member is `Positive` under its own source's config.
  - `func Detect(links []calendar.Link, bySource map[string]config.ConflictConfig, dismissed map[string]time.Time) []Conflict`: pairs of distinct links whose canonical ranges overlap (`a.Start < b.End && b.Start < a.End`; zero-duration never overlaps) and where both `LinkPositive`. Key is the first 16 hex chars of sha256 over the two `Key|start|end` strings sorted lexicographically. `Tentative` true if either side's canonical `IsTentative()`. `Dismissed` true if the key is in `dismissed`.
